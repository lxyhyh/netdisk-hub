## 1. 判定规则（照抄 T-005 卡，不因结果调整）

以下规则在 T-005 卡中已经定死，本文不改动任何一条：

1. **硬准入条件**：原生登录可行性 = **可行**
   - 「需攻关」：可进候选，但**必须先完成攻关任务**，完成前不计入 Go 的分子；
   - 「不可行」/「未知」：**出 MVP**。
2. **候选排序维度**（仅在可行集合内使用）：协议差异度 > 客户端校验强度（低优先）> 静态资料完整度（高优先）。
3. **MVP 锁定 2 个网盘**：一个偏「简单可跑通」，一个偏「有差异能验证抽象」。
4. **Go/No-Go 判定**：
   - Go：可行集合 ≥ 2 个；
   - No-Go：可行集合 < 2 个。

四档结论的定义（T-002c 已定，本文沿用）：

| 结论 | 判定条件 |
|---|---|
| **原生登录可行** | 有完整证据证明可通过官方客户端协议，在本项目自己的 APP 内主动换取会话，不依赖 OAuth、WebView、网页 cookie 等不合格路径 |
| **需攻关** | 已确认存在符合项目要求的官方客户端原生认证路径，但签名、设备指纹、版本校验、native 注入等关键环节仍需解决 |
| **不可行** | 已有证据证明官方客户端协议不满足项目登录约束，或命中项目已批准的资料缺失兜底规则 |
| **未知** | 当前资料不足，不能证明可行或不可行 |

三条禁止的等价替换（T-002c 已写明，本文重申）：

- 「需攻关」≠「可行」；
- 「未知」≠「不可行」；
- 「官方 APP 有登录页面」≠「本项目可独立实现」。

## 4. No-Go 决策

### 4.1 决策内容

- **T-005 结论：No-Go。**
- **不锁定两个 MVP 网盘。**
- **不启动阶段 2 的单网盘 Provider 实现。**
- 补救路径：选定一个「需攻关」候选，先完成阶段 0 的攻关任务（见第 7 节 → T-006），攻关完成后再重新评估 Go/No-Go。

### 4.2 为什么不能「凑」两个

三重原因，任何一条都足以否掉：

1. **规则层面**：T-005 的硬准入写死为「可行」。把「需攻关」或「未知」算进分子就是修改规则，而规则明确「不因结果调整」。
2. **工程层面**：T-002c 已证明，三家「需攻关」的阻断点集中在同一类东西上——闭源 native 安全组件（见 6.1）。在未解决该阻断点前锁定它们，等于把阶段 2 的前提押在一个尚未验证的假设上。
3. **项目层面**：`AGENTS.md` 第 9 条禁止以 OAuth / WebView / cookie 等降级方式换取登录。凑数最省事的做法恰恰是降级，而这条线不能碰。

### 4.3 不降低门槛（六条硬记录）

1. 「需攻关」只有在**攻关完成并达到「原生登录可行」**之后，才可以计入 Go 数量。
2. 「未知」不得进入阶段 2。
3. 「不可行（资料缺失）」直接从 MVP 移除，不重新讨论。
4. 不得采用 OAuth、WebView 登录、cookie 提取、手动粘贴 token 作为替代方案。
5. 不得因为某个网盘「资料多 / 好实现」而跳过硬准入。
6. 不得把「官方 APP 自己能登录」当作本项目可独立实现的证据。

## 5. 坚果云的特殊核对（人机验证与动态验证边界）

坚果云是当前唯一的「可行」，因此必须把它唯一的不确定点单独查清。本节内容全部为**静态代码事实**，运行时行为一律 **待确认**。

### 5.1 事实：验证码是什么、在哪、怎么被触发

**（1）登录请求里有两组验证码相关字段**

`connection/w.java:171-196`（解密版同段）构造 `/mcmd/loginV2` 的 JSON body，共 9 个字段：

| 字段 | 来源 |
|---|---|
| `userName` / `password` | 均经 `utils/y.java:124-126` 的 `H()`（单向 Base64，无 MD5/SHA） |
| `tfPasscode` | 二次验证码，非空才写入 |
| `custom_ticket` / `exp` / `sig` / `reusable` | 来自 `/mcmd/getCaptchaV2` 的 `CaptchaResponse` |
| `ticket` / `randstr` | 来自**人机验证**（腾讯验证码控件）的回调 |

**（2）触发顺序（已验证）**

| 跳 | 位置 | 动作 |
|---|---|---|
| 1 | `v2/ui/login/m.java:21` | `h(user, pass, tfPasscode, ticket, randstr)` 五参入口 |
| 2 | 同文件 `:22-25` | 若 `ticket` 为空 → 走 `D(...)` 先**预取验证码** |
| 3 | 同文件 `:58-60` | `rx.Observable.create(new y(this, str))` → `GET /mcmd/getCaptchaV2` |
| 4 | `v2/ui/login/f.java:29-35` | `onNext(CaptchaResponse)`：`isNeedRealCaptcha()` 为真 → 弹人机验证；为假 → 直接 `this.I.h(...)` 发登录 |
| 5 | `v2/ui/login/LoginActivity.java:83-85` | `findViewById(R.id.frame_login_verify_coder)` 取 `TencentCaptchaView`，注册回调 `v2/ui/login/c.java` |
| 6 | `v2/ui/login/c.java:14-18` | 回调 `D(ticket, randstr)` → 带两者回到 `m.java:21` 重入 → 这次 `ticket` 非空，直接发登录 |

**（3）控件实现（已验证，关键）**

`v2/ui/signup/TencentCaptchaView.java`：

- 它是一个 `android.widget.FrameLayout`，内部 `new WebView(context)`（`:29`）；
- `loadUrl("file:///android_asset/TencentCaptchaH5.html?appid=%1s&language=%2s")`（`:73`，URL 模板由字符串解密还原，密钥 `0x61`）；
- 该 HTML 是 APK 内 `assets/TencentCaptchaH5.html`（1522 B），内容为：`<script src="https://turing.captcha.qcloud.com/TJCaptcha.js"></script>` + `new TencentCaptcha(appid, callback, options)` + 回调里 `window.jsBridge.getData(JSON.stringify({ret, randstr, ticket}))`；
- 结果经 `TencentCaptchaView.java:95-118` 的 `D(String)` 解析 JSON（`ret==0` 取 `ticket`/`randstr`）。

### 5.2 四个问题，逐条回答

**问题 1：该验证码是否只是服务端条件触发的交互环节？**

**是（已验证）。** 触发开关是服务端返回的 `isNeedRealCaptcha()`（`f.java:29-35`）。客户端在 `isNeedRealCaptcha()` 为假时**完全不弹验证码**，直接发 `/mcmd/loginV2`。也就是说：验证码是**条件分支**，不是每次登录必经。

**问题 2：是否要求移植闭源 SDK 或依赖官方 App 进程？**

**不要求依赖官方 App 进程，但依赖第三方闭源服务（已验证）。**

- 控件本身是**本项目可直接复制的纯客户端代码**（`FrameLayout` + `WebView` + 本地 HTML），不需要官方 App 进程存活，不需要 IPC、不需要 hook；
- 但真正生成 `ticket`/`randstr` 的是**腾讯验证码服务**：HTML 从 `turing.captcha.qcloud.com` 拉取 `TJCaptcha.js`，挑战与校验都在腾讯侧完成；
- 因此依赖性质是「**第三方闭源 Web 服务 + 其 JS**」，不是「闭源 native SDK」（对比：夸克 / 阿里依赖的是阿里聚安全 **native so**）。

**问题 3：本项目是否能够通过自己的 UI 和请求流程完成该交互？**

**部分可以，但不是「纯 Rust 独立实现」（判断，基于已验证事实）。**

- 可以的部分：登录凭证交换（`/mcmd/loginV2`）全程是原生 HTTP + JSON，本项目可用 Rust 直接实现；验证码只是往 body 里多填 `ticket`/`randstr` 两个字符串。
- 不可以的部分：`ticket`/`randstr` 的合法性由腾讯服务端判定，纯 Rust 自研无法生成被接受的票据。可行做法只有两种：
  - (a) 在 App 内嵌一个 WebView 加载同一份腾讯 H5（**等价于官方 App 的做法**）；
  - (b) 改用腾讯验证码的其它端方案（如无感 / 服务端校验），可用性 **待确认**。
- 也就是说：**这一分支存在「第三方 WebView 依赖」**，但它不构成登录授权降级——凭证仍由本项目原生协议直接交换，不经 WebView 提取 cookie / token。

**问题 4：UA 校验、验证码触发阈值是否经过真实服务端验证？**

**没有，全部未验证（待确认）。**

| 项 | 现状 | 可信度 |
|---|---|---|
| UA 是否硬校验 | `HttpConfig.java:32-34` 由 `Build.VERSION.RELEASE` / `Build.MODEL` / 版本号拼 `NutstoreApp-Android-*` 四段；服务端是否比对 | **待确认** |
| 验证码触发阈值 | `isNeedRealCaptcha()` 由服务端给，触发条件（IP / 频率 / 设备 / 账号风险）未知 | **待确认** |
| `tfPasscode` 启用条件 | 二次验证码的业务开关未知 | **待确认** |
| token 服务端有效期 | 客户端无过期字段，靠 `AccountExpired` 兜底 | **待确认** |

### 5.3 分类是否要调整：结论

**维持「原生登录可行（静态可行，动态未验证）」，但把验证码分支登记为显式风险，并写死降级触发条件。**

判断依据（三层逐条）：

| 层 | 判断 | 依据 |
|---|---|---|
| 第 1 层 界面存在 | 满足 | 有 `LoginActivity` 原生登录页 |
| 第 2 层 协议存在 | 满足 | 请求构造（`w.java:171-196`）+ 响应解析（`LoginSignupResponse.java:12-14`）+ 落库（`utils/ja.java:30-60`）+ 注入（`HttpConfig.java:36-43`）四段闭环 |
| 第 3 层 独立实现可行 | **主路径满足；验证码分支带条件性第三方依赖** | 主登录无 OAuth、无 WebView、无 cookie、无 native 签名、无设备指纹；验证码分支需腾讯 H5 |

**为什么主路径仍判「可行」**：四档定义里的「不依赖 OAuth、WebView、cookie」针对的是**登录凭证的获取路径**。坚果云的凭证由本项目原生协议直接交换，WebView 只出现在「反机器人挑战」这一步，且这与官方 App 的做法完全一致，不构成授权降级。

**降级触发条件（写死，供后续动态验证后复用）**：

> 若动态验证证明以下两条**同时成立**，坚果云应按四档标准从「原生登录可行」下调为「需攻关」：
> (a) 常规请求（非异常频率、正常 UA）**必然触发** `needRealCaptcha`；
> (b) 项目决定**不接受**在 App 内嵌腾讯验证码 H5。
>
> 只满足 (a) 而接受 (b) 的嵌入方案，则维持「可行」，但验证码分支必须记录为已知实现项。

**Go 数量不变**：无论是否下调，可行数量都 ≤ 1，**No-Go 结论不依赖这一项**，也没有任何人为抬高数量的操作。

### 5.4 动态验证未完成的边界

本文与 T-002c 的所有坚果云结论都是**静态发现**。以下事情**没有做**，因此不能宣称「坚果云已可实际登录」：

- 没有发送任何真实登录请求；
- 没有验证 UA 是否被服务端接受；
- 没有验证验证码是否会触发；
- 没有验证 `/mcmd/loginV2` 的响应格式与字段名是否与静态代码一致；
- 没有测试 token 在后续文件接口中的实际有效期。

这些属于阶段 2 的动态验证，需用户单独授权后执行。

### 6.2 排序依据（为什么是 1 百度 / 2 夸克 / 3 阿里）

1. **百度排第一，是因为「可独立实现的部分最多」**：
   - 登录三通道的协议链路已全部找到（第 2 层已满足，不是猜的）；
   - 密码 / 短信两条主链的加密算法全在 Java 层，Rust 可复刻；
   - 最关键的 `Sdata` 签名**根本不在 sapi2 登录链路上**（在 `classes2` / `classes12` 搜 `Sdata` **0 命中**），这一点排除了一个原本被误认为致命的阻断；
   - 剩下的问题是「参数从哪来」（`tpl` / `appSignKey` / `di` 裁剪），属于**可以继续挖**的静态问题，不是「必须移植闭源 so」。
2. **夸克排第二，是因为阻断点单一但硬**：登录协议本身已读完，唯一卡点是「请求体加密 + 签名」两处都依赖阿里聚安全 native。单点、明确、但绕不过。
3. **阿里排第三，是因为阻断点最多且尚未挖完**：除聚安全 native（签名 + riskControlInfo）外，`AccountRpc` 未反编译、Havana 二维码流程字段未读，**静态还有欠账**——资料都没读完就谈攻关顺序是不严谨的。

### 6.3 必须写清的边界：百度不是「已经可行」

以下四点仍**未解决**，因此百度维持「需攻关」：

| # | 未解决项 | 为什么它重要 |
|---|---|---|
| 1 | `tpl` / `appSignKey` 的运行时取值来源未定位 | 二者是 sapi2 配置的必需项（`SapiConfiguration.java:523-524` 空值直接抛 `IllegalArgumentException`），缺了就构造不出请求 |
| 2 | `di` 40 字段的必需 / 条件 / 可选划分未知 | 字段缺失或格式错误可能导致服务端风控拒绝，无法靠猜 |
| 3 | `passport_core` 在**选定登录路径**中的实际作用未定 | 目前证据显示不在账号密码 / 短信主链，但「未在调用点出现」不等于「运行期不需要」 |
| 4 | 服务端风控是否放行未知 | 静态无法回答，只有真实请求能回答（且需用户授权） |

**因此：T-005 不因「百度看起来更好做」就把它算进 Go 数量。**

## 附录 A：一句话回答「为什么现在没有锁定两个 MVP 网盘」

> 因为按写死的硬准入标准，九个网盘里只有坚果云一家达到「原生登录可行」，其余八家里三家「需攻关」、两家「未知」、三家「不可行」，可行数量 1 < Go 门槛 2。
> 规则不允许把「需攻关」或「未知」算进分子，也不允许用 OAuth / WebView / cookie 降级凑数，所以只能判 No-Go，先攻关一家，再重评。

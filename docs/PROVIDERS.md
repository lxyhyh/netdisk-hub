### 关于「Flutter 主体」的含义

天翼云盘、123云盘、夸克网盘、阿里云盘的业务逻辑编译在 `libapp.so`（Dart AOT），
**静态反编译 dex 拿不到网盘协议**，只能得到入口壳与原生桥接。这直接影响静态侦察的
投入产出比（详见 docs/evidence/apk-inventory.md 第 3.1 节）。

### 列定义

**原生登录可行性**

- **可行**：APP 内原生登录可完成，走官方客户端协议
- **需攻关**：原生登录可行但需解决签名/设备指纹/版本校验等
- **不可行（协议不合格）**：只能走 OAuth/WebView/cookie，且官方客户端协议本身不许可原生登录
- **不可行（资料缺失）**：现有 APK 无法支撑官方协议还原，无法判定可行性 —— 按"不可行"处理
- **未知**：资料不足，待侦察

> 三档"不可行"都**不进 MVP**。区别只在原因归属：协议不合格 vs 资料缺失。

**登录类型**

- 账号密码
- 短信验证码
- 扫码
- 混合（多种方式并存）
- OAuth（不合格）
- 未知

## 4. 准入规则

## 6. 纵向切片建议

> **状态：T-002b 后已复核（2026-11-26），原建议不再成立。以下保留原文 + 复核结论，待拍板。**

### 6.1 原建议（T-001 时给出，基于结构特征，无接口证据）

**建议先做：天翼云盘 + 坚果云。**

理由：

1. **认证方式差异大**：天翼是运营商体系（短信/账号密码），坚果云是独立
   WebDAV 风格账号体系，两者登录协议完全不同 —— 能真正验证 `connect` 抽象。
2. **上传协议差异大**：天翼走云盘协议（分片、可能秒传），坚果云有 WebDAV
   语义，两者上传实现无重叠 —— 能真正验证 `upload` 抽象。
3. **资料可得性**：两者 APK 都在手，且天翼已确认非 Flutter 主体
   （虽有 Flutter 运行时）；坚果云仅 2 dex、无加固，是最容易侦察的一个。
4. **风险分散**：一个高风险（天翼，运营商风控）配一个低风险（坚果云，
   协议相对透明），避免两个都卡在同一类问题上。

**备选**：若天翼风控过重，用 123云盘 替换（同为简单账号体系，但为 Flutter）。

### 6.2 T-002b 复核结论

**T-002b 的实测结果推翻了原建议的两条依据。**

| # | 原依据 | 复核结果 |
|---|---|---|
| 1 | 天翼认证方式与坚果云差异大，能验证 `connect` | **无法验证。** 天翼尚未侦察，认证方式仍为「未知」，差异度无从判断（依据是推测，非事实） |
| 2 | 天翼上传协议差异大（分片/秒传） | **同上，纯推测。** 无任何证据表明天翼用分片上传 |
| 3 | "天翼已确认非 Flutter 主体" | **事实错误。** `docs/evidence/apk-inventory.md` §3 与 §3.1 明确记载天翼云盘是 **Flutter 主体**（`assets/ijm_libexec.so`、`libexecmain.so`、`libsecurity.so`），jadx 反编译 dex 拿不到网盘协议 |
| 4 | 坚果云最容易侦察 | **成立。** T-002b 实测：2 dex、无加固、无证书绑定，8006 个类全静态可读，已产出完整索引 |

**新增的反向证据**：

- **天翼云盘 APK 387 MB，是 9 个网盘里最大的一个**，且为 Flutter 主体。
  按 T-002b 的实测经验，对 Flutter 主体做静态侦察的产出接近于 0
  （见 `index-坚果云.md` §11.5），也就是说**天翼连"资料可侦察"这一条都不满足**。
- 反过来，坚果云已具备最完整的静态资料，是唯一一个**当前就能写代码**的。
